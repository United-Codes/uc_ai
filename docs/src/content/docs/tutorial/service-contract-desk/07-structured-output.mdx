## The problem

Every answer so far has been a paragraph of English. A person can read it. Your
application cannot.

An APEX page needs to put the answer in one region, show what the desk did in
another, and colour a badge when a human must decide. Parsing that out of prose
is guesswork, and the wording changes with the model.

**Without a schema,** your page gets one block of text. **With a schema,** it gets
named fields, and the model is not allowed to leave one out.

## Put the schema on the profile

The response schema belongs on the profile, next to the prompt it shapes.
`execute_agent` also takes a `p_response_schema`, but use that only for a one-off
override.

```sql
c_schema constant varchar2(2000 char) := '{
  "type": "object",
  "properties": {
    "answer":        { "type": "string",
                       "description": "The reply for the engineer, in one or two sentences" },
    "actions_taken": { "type": "array", "items": { "type": "string" },
                       "description": "What you did, one entry for each tool you used" },
    "needs_human":   { "type": "boolean",
                       "description": "True when a person must decide before anything else happens" },
    "confidence":    { "type": "string", "enum": ["low", "medium", "high"],
                       "description": "How sure you are of the answer" }
  },
  "required": ["answer", "actions_taken", "needs_human", "confidence"],
  "additionalProperties": false
}';
```

Two things make this schema useful rather than decorative:

- `"required"` names every field, so your page never has to handle a missing one.
- `"enum"` on `confidence` means you can put the three values in a `case`
  expression and know the list is closed.

## The change that breaks your earlier code

<Aside type="caution" title="final_message stops being text">
A response schema changes the **type** of `final_message`. Without a schema it is
text and `get_clob` reads it. With a schema it is a JSON **object**, and
`get_clob` returns nothing — no error, no warning, an empty string.

Every code sample in lessons 1 to 6 used `get_clob('final_message')`. All of it
goes quiet the moment you add a schema.
</Aside>

Here is that failure, from a real run:

```
get_clob  -> [(empty)]
```

Read it as an object instead:

```sql
declare
  l_result  json_object_t;
  l_answer  json_object_t;
  l_actions json_array_t;
begin
  l_result := uc_ai_agents_api.execute_agent(
    p_agent_code       => 'SC_DESK'
  , p_input_parameters => json_object_t('{"engineer_name":"Petra","today":"2026-08-24"
      ,"question":"Can I credit 350 on INV-1002? Check it properly."}')
  , p_session_id       => l_session
  , p_run_context      => json_object_t('{"contract_id":"88","engineer":"petra.k"}')
  );

  l_answer := l_result.get_object('final_message');

  sys.dbms_output.put_line(l_answer.get_string('answer'));
  sys.dbms_output.put_line(
    case when l_answer.get_boolean('needs_human') then 'true' else 'false' end);
  sys.dbms_output.put_line(l_answer.get_string('confidence'));
end;
/
```

`final_message` has three shapes across the whole framework, so read it
defensively in code you ship:

| Shape | When | How to read it |
| --- | --- | --- |
| CLOB | no response schema | `get_clob('final_message')` |
| JSON object | a response schema is set | `get_object('final_message')` |
| JSON null | the run produced no answer | test for it; `get(...).to_clob` gives the four characters `null` |

The answer now arrives in parts:

Your page can now render `answer` in a region, `actions_taken` as a list, and
`confidence` as a badge, without reading a word of English in PL/SQL.

## The schema did not stop the tools

This is the part worth checking yourself, because a strict schema can pull a model
toward answering immediately instead of calling a tool first. It did not here. The
same run made seven tool calls before it answered:

```
tool call   -> 3  MEMORY
tool call   -> 6  SC_GET_CONTRACT
tool call   -> 7  SC_LIST_INVOICES
tool call   -> 8  SC_LIST_CALLS
tool call   -> 13 MEMORY
tool call   -> 15 SC_RAISE_CREDIT_NOTE
tool call   -> 18 MEMORY
```

So the desk read the contract, the invoices and the calls, asked the database for
the credit note, was refused, and then reported that refusal in the `answer`
field. Structured output shapes the **last** message. It does not shorten the work
before it.

## Verification

Run the same question and check three things:

```sql
select m.seq
     , m.role
     , m.tool_name
  from uc_ai_agent_messages m
 where m.session_id = :session_id
   and m.role = 'tool_call'
 order by m.seq;
```

1. The trace holds `SC_RAISE_CREDIT_NOTE`, so the desk really asked.
2. No new row appeared in `sc_credit_notes`, because the database refused:

   ```sql
   select count(*) as should_be_one from sc_credit_notes;
   ```

3. The four fields of the schema are all present in `final_message`, and
   `confidence` is one of `low`, `medium`, `high`.


## Key takeaways

- Put the response schema on the profile, and name every field in `"required"` so
  your page never handles a missing one.
- A response schema changes `final_message` from text to an object. `get_clob`
  then returns empty with no error, which silently breaks working code.
- `l_answer := l_result.get_object('final_message');`
