**Code mode lets the model write a small program that calls your tools, instead of calling them one at a time.**

With normal [tool calling](/products/uc-ai/docs/guides/tools/), every tool call is a separate round-trip: the model asks for a tool, UC AI runs it, the result flows back into the model's context, the model asks for the next one, and so on. For data-heavy work — "fetch every employee, then their expenses, sum the approved travel" — that means many round-trips and a lot of raw tool output piling up in the context window.

Code mode collapses that into **one** call. The model authors a short JavaScript program; UC AI runs it inside the database via Oracle's Multilingual Engine (MLE); the program calls your tools in a loop, filters and aggregates locally, and returns **only its final result** to the model. The intermediate tool output never touches the model's context.

<Aside type="tip" title="When is it worth it?">
Code mode shines when a task needs **many tool calls**, **loops over lists**, or pulls **large intermediate data** that you only need to aggregate. For a single tool call it adds nothing — the model can just call the tool directly, and both options stay available.
</Aside>

## Requirements

Code mode is an **opt-in feature that requires Oracle Database 23ai** (for MLE JavaScript with `PURE` execution contexts). The rest of UC AI still runs on [Oracle 12.2+](/products/uc-ai/docs/other/faq/) — only this feature needs 23ai.

Because model-authored code is inherently untrusted, code mode **always runs inside a dedicated, locked-down sandbox** — there is no unsandboxed fallback. You must install that sandbox once, as a DBA:

```bash
# connect as SYS / a DBA to the same PDB where UC AI is installed
sql sys/<pwd>@<pdb> as sysdba

@scripts/install_ptc_sandbox.sql
```

The script asks for two schema names: the schema UC AI is installed in, and the sandbox schema to create for it (defaults `UC_AI` and `UC_AI_MLE_SBX`). It creates that schema-only account (`NO AUTHENTICATION`, cannot log in), a `PURE` MLE environment, the MLE runner, and a private synonym in your UC AI schema that points at the runner — which is how UC AI finds the sandbox at runtime, with no schema name compiled in.

Run it **once per UC AI installation**: two installations must not share one sandbox, because its gateway synonym points at a single UC AI schema. The script refuses a sandbox schema that already owns unrelated objects, and verifies afterwards that the runner compiled and the synonym points where it should.

Undo with `scripts/uninstall_ptc_sandbox.sql` (same two prompts). If you enable code mode without having installed the sandbox, `generate_text` raises a clear error telling you to run the script.

## The security model

This is the important part. **The model's JavaScript has no database access at all.**

- It is evaluated in a [`PURE` MLE execution context](https://docs.oracle.com/en/database/oracle/oracle-database/26/mlejs/restricted-execution-contexts.html), which removes every database-facing JavaScript API: `mle-js-oracledb` can be neither `require`d nor dynamically `import`ed, and the `oracledb` / `session` / `soda` / `plsffi` globals do not exist. The program cannot run a single SQL statement.
- Consequently it also cannot `COMMIT` or `ROLLBACK`. That matters: transaction control needs no privileges at all, so a privilege wall alone would not stop generated code from discarding your pending work.
- `callTool` is therefore **serviced from PL/SQL**: the program awaits a tool call, control returns to the runner, the runner calls the UC AI gateway, and the program resumes with the result. That is the only channel in or out.
- As defense in depth the runner is a **definer's-rights** package owned by the low-privilege sandbox schema, which is granted **nothing** except `EXECUTE` on that one gateway package (`uc_ai_ptc_api`) — no tables, no quota, no other packages.
- Your tools themselves still run with full UC AI privileges (the gateway is a UC AI package) and **in the caller's transaction**, exactly like a direct tool call — so tools stay in charge of their own transaction handling, and a tool that commits behaves the same either way.

<Aside type="caution" title="Tools are still real code">
The sandbox stops the model's *JavaScript* from doing anything except calling tools. It does **not** change what your *tools* do. A tool that deletes data can still be asked to delete data. Scope code-mode runs to safe, read-oriented tools with [tags](#enabling-code-mode) and keep write/destructive tools out of that set.
</Aside>

On top of that, UC AI enforces a per-run **allow-list** (a program may only call tools that were exposed for this run — the same enabled + tag-filtered set the model sees) and a **call budget** (a cap on tool calls per program) to bound runaway loops. The optional [`before_tool_call` hook](/products/uc-ai/docs/guides/agentic-ai/) fires for **every** `callTool` inside a program, not just for the program as a whole, so hook-based authorization and auditing keep working in code mode — and a veto aborts the whole request.

## Enabling code mode

Code mode builds on normal tool calling, so you enable tools as usual and add one flag:

```sql
begin
  uc_ai.g_enable_tools              := true;                 -- tools on
  uc_ai.g_enable_programmatic_tools := true;                 -- offer code mode
  uc_ai.g_tool_tags                 := apex_t_varchar2('reporting');

  declare
    l_result json_object_t;
  begin
    l_result := uc_ai.generate_text(
      p_user_prompt   => 'What is the total approved travel spend across all employees?'
    , p_system_prompt => 'You are a data analyst. Prefer writing a program with the '
                      || 'code tool over calling tools one by one.'
    , p_provider      => uc_ai.c_provider_anthropic
    , p_model         => uc_ai_anthropic.c_model_claude_4_6_sonnet
    );
  end;
end;
/
```

When `g_enable_programmatic_tools` is true, UC AI adds one extra tool, `uc_ai__run_code`, alongside your normal tools. Its description lists the exact tool codes the program may call. The model can still call tools directly — code mode is an *additional* option it picks when a task benefits from it.

### Choosing which tools are available where

By default every enabled tool is available **both** ways — directly and inside a program. You can narrow that per tool with `p_code_mode_access` on `create_tool_from_schema` / `merge_tool_from_schema`:

```sql
uc_ai_tools_api.merge_tool_from_schema(
  p_tool_code        => 'GET_EXPENSES'
, p_description      => 'Fetch expense rows for one employee'
, p_function_call    => 'return my_pkg.get_expenses(:parameters);'
, p_json_schema      => l_schema
, p_code_mode_access => 'code'   -- direct | code | both  (default 'both')
);
```

- `direct` — a normal tool only; **not** callable from a program. Use for actions you want the model to invoke deliberately (e.g. "send email", "delete record").
- `code` — hidden from the direct tool list, only callable via `callTool` inside a program. Use for bulk/read data tools: keeps them out of the model's tool list and their large output out of its context.
- `both` — available either way (the default).

This is enforced, not advisory: the allow-list rejects a `callTool` to a `direct`-only tool even if the model guesses its code. It only applies when code mode is on — with code mode off, every tool is a normal tool regardless of this setting.

<Aside type="note">
Code mode works with every provider that supports tool calling. In practice the more capable models write more reliable JavaScript — see the model-quality notes in the [Tools guide](/products/uc-ai/docs/guides/tools/#best-practices).
</Aside>

## How the program calls your tools

Inside the program the model calls:

```js
const data = await callTool("YOUR_TOOL_CODE", { some: "arg" });
```

- The program runs as the body of an **async function**, so `await` works at the top level.
- `await callTool(code, args)` returns the tool's result already parsed from JSON (an object or array). It must be awaited — the tool call is executed by PL/SQL, not by the JavaScript. If the model forgets the `await`, UC AI inserts it (string literals, comments and same-named member calls are left alone, and the original source is used if the rewrite would not parse); where that is impossible — an alias such as `const f = callTool` — the program fails with an explicit "callTool() is asynchronous" message instead of quietly treating the promise as data.
- The program returns its answer by assigning to a top-level variable named `result` (an object or a string). Only that value is sent back to the model.
- It's plain JavaScript — loops, `filter`, `reduce`, arithmetic. No SQL, no network, no file access, no modules.

A typical program the model writes looks like this:

```js
const employees = await callTool("GET_EMPLOYEES", {});
let total = 0;
for (const e of employees) {
  const expenses = await callTool("GET_EXPENSES", { employee_id: e.id });
  for (const x of expenses) {
    if (x.category === "travel" && x.status === "approved") total += x.amount;
  }
}
const result = { approved_travel_total: total };
```

That is a single `uc_ai__run_code` call. Only `{ approved_travel_total: ... }` returns to the model — none of the per-employee expense rows.

If the program throws, calls an unknown/disallowed tool, or exceeds the call budget, UC AI returns the error to the model **as data** so it can fix the program and try again on its next turn, rather than aborting the whole request.

## Limitations

- **Oracle 23ai only** (MLE JavaScript with `PURE` contexts). The sandbox must be installed first.
- **No per-program time limit** is enforced by MLE itself, so a pure-JavaScript infinite loop (one that never calls a tool) is only bounded by the Database Resource Manager. Tool calls themselves are bounded by the per-run call budget.
- The program can only call tools in the **current run's** enabled/tag-filtered set — tools outside it are rejected even if their code is guessed.
- Sub-agents registered as tools ([orchestrator / handoff](/products/uc-ai/docs/guides/multi-agent-systems/handoff/)) are `direct`-only: delegating to another agent costs LLM calls, so it stays a deliberate decision of the calling model rather than something a program can loop over.
