## The problem

The desk works. Now somebody else has to be able to use it, and somebody has to
pay for it. Three questions arrive together:

- Who asked, and what did it use?
- How does a person talk to it, when everything so far ran in SQLcl?
- How does any of this reach production, when my agent is a **row** and not a file?

## Who ran what

`uc_ai_agent_sessions` holds one row for each conversation, with the totals already
summed:

```sql
select s.turn_count
     , s.message_count
     , s.total_input_tokens
     , s.total_output_tokens
     , s.created_by
     , s.audience
     , nvl(s.title, '(no title)')       as title
     , nvl(s.feedback_rating, '-')      as rating
  from uc_ai_agent_sessions s
 where s.root_agent_id = ( select id from uc_ai_agents where code = 'SC_DESK' )
 order by s.started_at desc
 fetch first 5 rows only;
```

```
TURN_COUNT  MESSAGE_COUNT  TOTAL_INPUT_TOKENS  TOTAL_OUTPUT_TOKENS  CREATED_BY  AUDIENCE
         1              0                   0                    0  UC_AI       db
         1              8                 657                   76  UC_AI       db
         1              4                 549                   38  UC_AI       db
```

Three of those columns:

- **`audience`** separates a signed-in APEX user from an anonymous visitor from a
  database session. A username cannot do that, because every anonymous visitor of
  an app shares one APEX public user. The rows above say `db`, because they were
  started from SQLcl and from a scheduler job.
- **`created_by`** is the caller that UC AI can prove: the APEX user when there is
  one, the database user otherwise.
- **`message_count` is `0` on the first row.** That run failed. A failed run has
  no result object to read, so UC AI records no tokens and no messages for it, and
  `tool_calls_count` of `0` on such a row does not mean that no tool ran. Count the
  `tool_call` rows in `uc_ai_agent_messages` when you need the truth, as
  [lesson 4](/products/uc-ai/docs/tutorial/build-an-agent/04-see-what-it-did/)
  does.

### Tokens are recorded, prices are not

UC AI counts tokens. It does not know what your provider charges, and there is no
price column anywhere in the schema. Multiply the counts by your own rate:

```sql
select s.created_by
     , sum(s.total_input_tokens)  as input_tokens
     , sum(s.total_output_tokens) as output_tokens
  from uc_ai_agent_sessions s
 where s.started_at >= trunc(sysdate)
 group by s.created_by
 order by 2 desc;
```

One recorded run of this desk used **657 input and 76 output tokens**, which is
the order of magnitude to expect for a question with two tool calls.

<Aside type="tip" title="Spend limits are a separate product">
Per-model pricing, budgets and spend enforcement are part of
[Guardrails](/products/uc-ai/docs/guides/guardrails/). This lesson stays with what
core records: token counts.
</Aside>

### A title and a rating for each conversation

Two calls turn a session list into something you can report on:

```sql
begin
  uc_ai_agents_api.set_session_title(
    p_session_id => :session_id
  , p_title      => 'Credit note for INV-1001'
  );

  uc_ai_agents_api.set_session_feedback(
    p_session_id => :session_id
  , p_rating     => 'down'
  , p_comment    => 'Quoted the wrong coverage window.'
  );
end;
/
```

UC AI never sets either one itself. A thumbs-down next to a token count is how you
find out which prompts cost money and produce answers the engineer rejected.

## Put it in front of a person

Everything so far ran in SQLcl. A person needs a page.

A run takes seconds, and an APEX page submit cannot wait that long. A chat region
therefore has to store the question, run the agent in a background job, and poll
for the answer. You do not have to write that. The **APEX Chat plug-in** is a
region plug-in that already holds all three, and it needs three attributes:

- **Agent Code** names the agent: `SC_DESK`.
- **Agent Input Mapping** fills the three placeholders of the profile, with
  `&APP_USER.` for the engineer, a page item for the date, and `#USER_MESSAGE#`
  for what the engineer typed.
- **Agent Run Context** carries the contract the page is on, so the tools of
  lesson 3 stay bound to one record and the memory of lesson 6 stays keyed on it.

The plug-in writes every message to `uc_ai_chat_messages`, beside the execution
rows this lesson reads.

[Put an Agent in
APEX](/products/uc-ai/docs/tutorial/put-an-agent-in-apex/01-a-chat-region/) builds
that region on this desk, in six lessons. It covers what the plug-in does about a
conversation another user must not read, a page that moves to another contract
mid-conversation, and an audit trail that names the person who asked. The [APEX
Chat plug-in guide](/products/uc-ai/docs/guides/apex-chat-plugin/) lists every
region attribute.

## Ship it

Your prompt profile, your tools and your agent are **rows**. They are not in your
repository, and a deployment of your packages does not carry them. So the
deployment is a script.

`09_promote.sql` is that script. You can run it more than one time, so the same
file is the install and the upgrade:

<Steps>

1. **Tools** with `merge_tool_from_schema`, which is create-or-replace for a tool.

2. **The profile**, created when absent and updated when present, at an explicit
   version.

3. **The agent**, created when absent and left alone when present.

4. **Memory, then the two activations.** `enable_for_agent` writes the memory tag
   into the profile version the agent resolves to **now**, so it runs after the
   profile exists.

</Steps>

What the script does **not** carry:

| Not deployed | Why |
| --- | --- |
| The demo tables | Your real tables are already there |
| The run history | The history of a development schema is not production data |
| The memory stores | What the desk learned in development is not true in production |

A release log ends with this:

```
OBJECT    DETAIL
tools     4
profile   SC_DESK_PROFILE v1 active
agent     SC_DESK v1 active
memory    context on contract_id
```

### Switch it off, or remove it

Two different needs, two different calls:

```sql
-- Stop it answering. Keeps every row, and is reversible.
uc_ai_agents_api.change_status('SC_DESK', 1, uc_ai_agents_api.c_status_archived);

-- Remove it and everything that belongs only to it.
uc_ai_agents_api.purge_agent(p_code => 'SC_DESK');
```

`change_status` to `archived` is the kill switch. An archived agent no longer
resolves, so a queued job fails with an error instead of doing something you did
not want.

`purge_agent` removes every version of the agent, its executions, its sessions,
their messages, and the memory stores that belong to it alone. It **keeps** what
other things also use: a shared or global memory store, a session another agent
opened, and the prompt profile — a profile lives without an agent, and another
agent can use it. It also keeps a tool whose PL/SQL text names the agent, because a
tool only mentions it in a string.

<Aside type="caution" title="purge_agent deletes an audit trail">
`purge_agent` removes run history. Decide whether you are allowed to do that before
you run it in production. If you only want the agent to stop, archive it.
</Aside>

## Verification

```sql
select 'sessions' as what, to_char(count(*)) as detail
  from uc_ai_agent_sessions
 where root_agent_id = ( select id from uc_ai_agents where code = 'SC_DESK' )
union all
select 'tokens today'
     , to_char(nvl(sum(total_input_tokens + total_output_tokens), 0))
  from uc_ai_agent_sessions
 where started_at >= trunc(sysdate);
```

Two rows come back. `sessions` counts every conversation this course started, and
`tokens today` is what they cost in tokens. Multiply that by the rate of your
provider, because UC AI does not know it.

## What you built

Seven lessons ago the model could not see your data. Now:

- It reads four tables through tools that **cannot** name a contract, so an
  engineer on contract 88 can never be shown contract 99.
- It can raise a credit note, and the **database** decides whether that is allowed,
  in four conditions written in PL/SQL rather than in English.
- It remembers each contract between conversations.
- Every run is recorded: who, when, which tools, how many tokens.
- It is a set of rows, so one script moves it to another database.

## Key takeaways

- Core records tokens, not money. Multiply by your own rate, or use Guardrails for
  real spend control.
- An agent is a row, not a file. The deployment is a script that merges the tools,
  the profile and the agent, and it must be safe to run again.
- `uc_ai_agents_api.purge_agent(p_code => 'SC_DESK');` removes the agent and its
  history. `change_status(..., c_status_archived)` is the reversible one.
