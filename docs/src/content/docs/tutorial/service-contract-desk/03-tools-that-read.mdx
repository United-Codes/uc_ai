## The problem

The desk of lesson 2 has a name and a version, and it still says "I can't access
the contract records". A **tool** is a PL/SQL function that the model can call. The
model does not read your tables. It asks your function, and your function reads
your tables.

That raises the question this lesson exists for. If the model chooses the
arguments, and one argument is the contract, then the model chooses the contract.
An engineer on contract 88 must never get an answer about contract 99.

**Without the run context,** you have to trust the model to name the right
contract. **With the run context,** the model cannot name a contract at all.

## The three tools declare no contract

Look at what is missing from these schemas:

```sql
declare
  l_tool_id number;
begin
  l_tool_id := uc_ai_tools_api.merge_tool_from_schema(
    p_tool_code     => 'SC_LIST_INVOICES'
  , p_description   => 'List the invoices of the contract of this conversation, with '
                    || 'the parts amount, the labour amount, how much is already '
                    || 'credited, and how much is still uncredited.'
  , p_function_call => 'return sc_desk_pkg.list_invoices(:ARGUMENTS);'
  , p_json_schema   => json_object_t('{
      "type": "object",
      "properties": {
        "max_rows": { "type": "integer", "description": "How many invoices at most. Defaults to 20." }
      },
      "required": []
    }')
  , p_tags          => apex_t_varchar2('scdesk')
  );
end;
/
```

There is no `contract_id`. The full script registers `SC_GET_CONTRACT`,
`SC_LIST_CALLS` and `SC_LIST_INVOICES` the same way, and none of them takes a
contract.

The contract arrives another way. When you start the run, you pass a **run
context**. UC AI adds it to the arguments of every tool in that run, under the
reserved key `_ctx`, **after** the model produced them. No model sees that key, and
no model can set it.

```sql
l_result := uc_ai_agents_api.execute_agent(
  p_agent_code       => 'SC_DESK'
, p_input_parameters => json_object_t('{"engineer_name":"Petra","today":"2026-08-24",
      "question":"How much can I still credit on INV-1003, and is the call inside the coverage window?"}')
, p_session_id       => l_session
, p_run_context      => json_object_t('{"contract_id":"88"}')
);
```

The handler reads the contract from `_ctx`, never from the model:

```sql
function bound_contract_id(p_arguments in clob) return number
as
  l_args    json_object_t := json_object_t(p_arguments);
  l_context json_object_t := l_args.get_object(uc_ai.c_run_context_key);
begin
  if l_context is null then
    return null;
  end if;
  return to_number(l_context.get_string('contract_id'));
end bound_contract_id;
```

Every query then filters on that value:

```sql
where i.contract_id = l_contract_id
```

<Aside type="caution" title="Read the arguments by name">
Never count the keys of the argument object, and never walk all of them. Every tool
now receives `_ctx` as one extra key, so a handler that reasons about the *shape* of
the arguments changed meaning when the run context arrived — silently, with no
signature change. The `MEMORY` tool that UC AI ships had this defect. Read
`l_args.get_string('max_rows')`, not the shape. The [tools
guide](/products/uc-ai/docs/guides/tools/#what-you-must-know) has the details.
</Aside>

## Give the tools to the agent

Tools reach the model through the model configuration of the prompt profile. The
tag `scdesk` selects exactly these three, so the desk never sees another tool in
your schema.

```sql
declare
  l_profile uc_ai_prompt_profiles%rowtype;
  l_config  constant clob := '{
    "g_enable_tools": true,
    "g_tool_tags": ["scdesk"],
    "g_max_tool_calls": 8
  }';
begin
  l_profile := uc_ai_prompt_profiles_api.get_prompt_profile('SC_DESK_PROFILE', 1);

  uc_ai_prompt_profiles_api.update_prompt_profile(
    p_code                   => l_profile.code
  , p_version                => l_profile.version
  , p_description            => l_profile.description
  , p_system_prompt_template => l_profile.system_prompt_template
  , p_user_prompt_template   => l_profile.user_prompt_template
  , p_provider               => l_profile.provider
  , p_model                  => l_profile.model
  , p_model_config_json      => l_config
  , p_parameters_schema      => l_profile.parameters_schema
  );
  commit;
end;
/
```

This changes **version 1**, the version the agent already resolves to. It does not
make a version 2, so the agent needs no change.

## What changed

The desk now answers from your tables:

<AiOutput model="gpt-5.6-terra" date="2026-08-24" seconds={4.2}>
INV-1003 has $0 still available to credit; its full $200 has already been credited.

The related call (2026-08-14) is inside the coverage window.
</AiOutput>

Compare that with lesson 1, where the model said "up to 200" from the same
question. The number is now right because the model stopped guessing and asked.

## Verification, part 1: no tool declares a contract

```sql
select t.code
     , nvl(( select listagg(p.name, ', ' on overflow truncate)
                     within group (order by p.name)
               from uc_ai_tool_parameters p
              where p.tool_id = t.id ), '(none)') as declared_parameters
  from uc_ai_tools t
 where t.code like 'SC\_%' escape '\'
 order by t.code;
```

```
CODE                 DECLARED_PARAMETERS
SC_GET_CONTRACT      (none)
SC_LIST_CALLS        max_rows
SC_LIST_INVOICES     max_rows
```

No row names a contract, and none can. `_ctx` is a reserved name: a tool that
declares it is refused at registration with `ORA-20503`. That holds for a nested
property, and it ignores upper and lower case.

<Aside type="note" title="Roll back after a refused registration">
`create_tool_from_schema` writes the tool row first, then checks the parameters. So
a refused registration leaves a tool row with no parameters behind, until you roll
back. If you try the `_ctx` rejection yourself, run `rollback` afterwards.
</Aside>

## Verification, part 2: prove the isolation without a model

The answer above proves the model *did not* ask for another contract. It does not
prove it *could not*. So call the handler directly, and lie to it: put contract 99
in the arguments, where a model would put it, and bind the run to 88.

```sql
declare
  l_args json_object_t;
  l_out  json_object_t;
begin
  l_args := json_object_t('{"max_rows":50,"contract_id":99}');
  l_args.put(uc_ai.c_run_context_key, json_object_t('{"contract_id":"88"}'));

  l_out := json_object_t(sc_desk_pkg.list_invoices(l_args.to_clob));
  sys.dbms_output.put_line('invoices returned: ' || l_out.get_number('count'));
end;
/
```

```
arguments said contract_id=99, _ctx said 88
invoices returned: 3
{"invoices":[{"invoice_no":"INV-1003", ... "credited_amount":200, ...
```

Three invoices, and all three belong to contract 88. Contract 99 has one invoice,
`INV-2001`, and it does not appear. The forged argument was ignored, because the
handler never reads it.

This is the check to keep. A model that declines to ask is being polite. A handler
that cannot answer is being safe.

<Aside type="caution" title="The run context binds arguments, not tool lists">
`_ctx` decides what a tool answers. It does not decide which tools the agent has.
A carefully bound `SC_LIST_INVOICES` gives no protection when the same tag set also
holds a tool that can read any table. Give the desk only tools that the run context
can bind.
</Aside>

## Key takeaways

- Leave the scoped value out of the tool schema. Then the model cannot name it, and
  there is one place the value can come from.
- Prove isolation by calling the handler with a forged value. A model that chooses
  not to ask has proved nothing.
- `p_run_context => json_object_t('{"contract_id":"88"}')` reaches every tool of the
  run under `uc_ai.c_run_context_key`.

**Full reference:** [The run
context](/products/uc-ai/docs/guides/tools/#the-run-context) covers `_ctx`, the
reserved name, and where else the run context applies.
