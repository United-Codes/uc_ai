## The problem

Every run in this course has taken between two and six seconds. A run that uses
more tools takes longer. Measured on the lessons so far:

| Run | Time |
| --- | --- |
| No tools (lesson 2) | 2.5s |
| One tool call (lesson 3) | 4.2s |
| Raise a credit note (lesson 5) | 5.2s |
| Seven tool calls (lesson 7) | longer still |

A page submit that blocks for five seconds is a bad page. A page submit that blocks
for twenty is a broken one, and a gateway between the browser and the database may
give up before the model does.

**Without a queue,** the page waits for the model. **With a queue,** the page writes
a row and comes back for the answer.

<Aside type="tip" title="You can build all of this before you touch APEX">
Nothing on this page needs an APEX object. The pattern is a table, a function the
page calls, and a procedure a job runs. Test it from SQLcl first, then wire a page
to it.
</Aside>

<Aside type="note" title="A plug-in does this for a chat page">
This lesson builds the pattern so that you know how it works. For a chat
interface you do not have to write it. The [APEX Chat
plug-in](/products/uc-ai/docs/guides/apex-chat-plugin/) is a region plug-in with
the same queue, the same job, and the same poll inside it. Build this lesson to
learn the pattern. Use the plug-in when you want a chat region.
</Aside>

## One table carries the request and the answer

```sql
create table sc_ai_requests (
  id           number generated by default on null as identity
, contract_id  number not null
, engineer     varchar2(255 char) not null
, question     varchar2(1000 char) not null
, status       varchar2(20 char) default on null 'queued' not null
, answer       clob
, error_text   varchar2(4000 char)
, requested_at timestamp default on null systimestamp not null
, finished_at  timestamp
, constraint sc_ai_requests_pk primary key (id)
, constraint sc_ai_requests_status_ck check (status in ('queued', 'running', 'done', 'failed'))
);
```

`status` is the column the page polls. The check constraint keeps the list closed,
so a dynamic action can branch on four values and no others.

## The page queues, the job answers

`queue_request` inserts the row, starts a job, and returns the id at once:

```sql
function queue_request(
  p_contract_id in number
, p_engineer    in varchar2
, p_question    in varchar2
) return number
as
  l_request_id number;
begin
  insert into sc_ai_requests (contract_id, engineer, question)
  values (p_contract_id, p_engineer, p_question)
  returning id into l_request_id;

  commit;

  sys.dbms_scheduler.create_job(
    job_name   => 'SC_AI_JOB_' || l_request_id
  , job_type   => 'PLSQL_BLOCK'
  , job_action => 'begin sc_desk_job_pkg.run_request(' || l_request_id || '); end;'
  , enabled    => true
  );

  return l_request_id;
end queue_request;
```

`run_request` does the slow part, and it always writes a final status:

```sql
l_result := uc_ai_agents_api.execute_agent(
  p_agent_code       => 'SC_DESK'
, p_input_parameters => json_object_t(
    json_object('engineer_name' value l_row.engineer
              , 'today'         value to_char(sysdate, 'YYYY-MM-DD')
              , 'question'      value l_row.question))
, p_session_id       => uc_ai_agents_api.generate_session_id
, p_run_context      => json_object_t(
    json_object('contract_id' value to_char(l_row.contract_id)
              , 'engineer'    value l_row.engineer))
);

-- Read the JSON in PL/SQL, into a local CLOB.
l_answer := l_result.get_clob('final_message');

update sc_ai_requests
   set status = 'done', answer = l_answer, finished_at = systimestamp
 where id = p_request_id;
commit;
```

<Aside type="caution" title="Do not read the JSON inside the UPDATE">
Putting `l_result.get_clob('final_message')` in the `UPDATE` itself raises:

```
ORA-40573: invalid use of PL/SQL JSON object type
```

A JSON object is a PL/SQL type, and SQL cannot use it. Read it into a local `clob`
first, then update with that variable.

The symptom is confusing: the **agent run succeeds** and its execution row says
`completed`, while your request row says `failed`. Two tables disagreeing like that
always means the failure came after the run, in your own code.
</Aside>

A run that raises must still leave a final status, or the page polls a row stuck
at `running` forever:

```sql
exception
  when others then
    l_error := sqlerrm;
    update sc_ai_requests
       set status = 'failed', error_text = l_error, finished_at = systimestamp
     where id = p_request_id;
    commit;
```

## The credential works with no browser session

A scheduler job has no APEX session, so an APEX web credential has nothing to
hang off. **UC AI creates its own APEX session** when none exists, which is what
lets the provider call succeed from a job, a trigger, or a nightly batch.

It does not pretend a person was there. The execution row of the job run records:

```
CREATED_BY   AUDIENCE   APEX_USER   TOOL_CALLS_COUNT   STATUS
UC_AI        db         (null)                     1   completed
```

`audience` is `db`, and `apex_user` is null, because the synthetic session is
stripped out of the audit trail. So a run from a job is recorded as a run from the
database, and lesson 9 can tell the two apart.

## Wiring the APEX page

The steps below build the page by hand, which is what this lesson teaches. The
[APEX Chat plug-in](/products/uc-ai/docs/guides/apex-chat-plugin/) replaces all
four steps with one region.

<Steps>

1. **Page items.** `P1_CONTRACT_ID` (the record the page is on), `P1_QUESTION`
   (what the engineer types), and `P1_REQUEST_ID` (hidden).

2. **A button** with a page process that calls the function and stores the id:

   ```sql
   :P1_REQUEST_ID := sc_desk_job_pkg.queue_request(
     p_contract_id => :P1_CONTRACT_ID
   , p_engineer    => :APP_USER
   , p_question    => :P1_QUESTION
   );
   ```

   Pass `:APP_USER` here. Inside the run, `APEX$SESSION` gives you the synthetic
   user instead, which is the trap from
   [lesson 5](/products/uc-ai/docs/tutorial/service-contract-desk/05-tools-that-write/).

3. **A region** over `sc_ai_requests`, filtered to `:P1_REQUEST_ID`, showing
   `status`, `answer` and `error_text`.

4. **A dynamic action** on a timer that refreshes the region, and stops when
   `status` is `done` or `failed`.

</Steps>

## Verification

Queue one request and poll it the way the page would:

```sql
declare
  l_request_id number;
  l_status     sc_ai_requests.status%type;
  l_waited     pls_integer := 0;
begin
  l_request_id := sc_desk_job_pkg.queue_request(
    p_contract_id => 88
  , p_engineer    => 'petra.k'
  , p_question    => 'Which invoices still have an uncredited amount?'
  );
  sys.dbms_output.put_line('Queued request ' || l_request_id || ', returned at once.');

  loop
    select status into l_status from sc_ai_requests where id = l_request_id;
    exit when l_status in ('done', 'failed') or l_waited >= 60;
    sys.dbms_session.sleep(2);
    l_waited := l_waited + 2;
  end loop;

  sys.dbms_output.put_line('After ' || l_waited || ' seconds the status is ' || l_status || '.');
end;
/
```

```
Queued request 1, returned at once.
After 4 seconds the status is done.
- INV-1001 — $780 uncredited (in coverage)
- INV-1002 — $350 uncredited (outside coverage)
```

Two things to check:

1. `queue_request` returned **before** the answer existed.
2. The row reached `done`, and the answer is in `sc_ai_requests.answer` where a
   region can read it.


## Before real users touch it

Three things this pattern does not solve, and each needs a decision from you:

- **Concurrency.** Twenty engineers asking at once means twenty jobs and twenty
  HTTP calls. The scheduler has a job limit, and your provider has a rate limit.
  Measure it before you promise it.
- **Retry.** A failed row holds the error. Nothing retries it. Decide whether a
  retry is safe first: a run that already raised a credit note must not raise a
  second one.
- **The kill switch.** `change_status('SC_DESK', 1, 'archived')` stops the agent
  resolving at once, and every queued job then fails with a clear error rather than
  doing something you did not want.

## Key takeaways

- A run takes seconds, so a page must not wait for it. Queue a row, answer it in a
  job, and poll the status.
- A JSON object cannot be used inside a SQL statement. Read `final_message` into a
  local `clob` before the `UPDATE`, or you get `ORA-40573`.
- `l_request_id := sc_desk_job_pkg.queue_request(p_contract_id => 88, p_engineer => :APP_USER, p_question => :P1_QUESTION);`

hooks](/products/uc-ai/docs/guides/execution-hooks/) covers what runs before and
