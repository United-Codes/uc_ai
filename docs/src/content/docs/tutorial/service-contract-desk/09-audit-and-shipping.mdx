## The problem

The desk works. Now somebody else has to be able to run it, pay for it, and switch
it off. Three questions arrive together:

- Who asked, and what did it use?
- Can I stop it doing something, without changing the prompt?
- How does any of this reach production, when my agent is a **row** and not a file?

## Who ran what

`uc_ai_agent_sessions` holds one row for each conversation, with the totals already
summed:

```sql
select s.turn_count
     , s.message_count
     , s.total_input_tokens
     , s.total_output_tokens
     , s.created_by
     , s.audience
     , nvl(s.title, '(no title)')       as title
     , nvl(s.feedback_rating, '-')      as rating
  from uc_ai_agent_sessions s
 where s.root_agent_id = ( select id from uc_ai_agents where code = 'SC_DESK' )
 order by s.started_at desc
 fetch first 5 rows only;
```

```
TURN_COUNT  MESSAGE_COUNT  TOTAL_INPUT_TOKENS  TOTAL_OUTPUT_TOKENS  CREATED_BY  AUDIENCE
         1              0                   0                    0  UC_AI       db
         1              8                 657                   76  UC_AI       db
         1              4                 549                   38  UC_AI       db
```

Three columns are worth knowing well:

- **`audience`** separates a signed-in APEX user from an anonymous visitor from a
  database session. A username cannot do that, because every anonymous visitor of
  an app shares one APEX public user. The rows above say `db`, because they were
  started from SQLcl and from a scheduler job.
- **`created_by`** is the caller UC AI could prove: the APEX user when there is one,
  the database user otherwise.
- **`message_count` is `0` on the first row.** That run was stopped by the hook
  below, and a failed run persists no messages.

### Tokens are recorded, prices are not

UC AI counts tokens. It does not know what your provider charges, and there is no
price column anywhere in the schema. So the honest calculation is yours:

```sql
select s.created_by
     , sum(s.total_input_tokens)  as input_tokens
     , sum(s.total_output_tokens) as output_tokens
  from uc_ai_agent_sessions s
 where s.started_at >= trunc(sysdate)
 group by s.created_by
 order by 2 desc;
```

Multiply by your own rate. One recorded run of this desk used **657 input and 76
output tokens**, which is the order of magnitude to expect for a question with two
tool calls.

<Aside type="tip" title="Spend limits are a separate product">
Per-model pricing, budgets and spend enforcement are part of
[Guardrails](/products/uc-ai/docs/guides/guardrails/). This lesson stays with what
core records: token counts.
</Aside>

### Let the engineer tell you it was wrong

Two calls turn a session list into something you can report on:

```sql
begin
  uc_ai_agents_api.set_session_title(
    p_session_id => :session_id
  , p_title      => 'Credit note for INV-1001'
  );

  uc_ai_agents_api.set_session_feedback(
    p_session_id => :session_id
  , p_rating     => 'down'
  , p_comment    => 'Quoted the wrong coverage window.'
  );
end;
/
```

UC AI never sets either one itself. A thumbs-down next to a token count is how you
find out which prompts cost money and produce bad answers.

## Stop a tool call with a hook

An **execution hook** is a package you write. UC AI calls it before and after every
run, and before every tool call. It is where a rule that has nothing to do with the
prompt belongs.

The contract is three procedures. `before_execution` and `after_execution` are
required; `before_tool_call` is optional, and UC AI detects whether your package
has it.

```sql
procedure before_tool_call(
  p_agent_id    in number
, p_agent_code  in varchar2
, p_tool_code   in varchar2
, p_created_by  in varchar2
, p_session_id  in varchar2
, p_apex_app_id in number
)
as
  l_hour pls_integer := to_number(to_char(systimestamp, 'HH24'));
begin
  -- A read is allowed at any time. A write is not.
  if p_tool_code = 'SC_RAISE_CREDIT_NOTE'
     and (l_hour < c_open_hour or l_hour >= c_close_hour)
  then
    raise_application_error(-20990
      , 'The desk cannot raise a credit note outside office hours.');
  end if;
end before_tool_call;
```

Register it **for your session** while you are learning:

```sql
begin
  uc_ai_agents_api.set_execution_hook('SC_DESK_HOOK');
end;
/
```

<Aside type="caution" title="UC_AI_HOOK activates itself for everything">
A valid package named `UC_AI_HOOK` in the schema is picked up automatically, with no
registration call, for **every agent and every session**. That is the right shape
for production and the wrong shape for an experiment: compile it and you have
changed the behaviour of every agent in the schema, including other people's.

Use `set_execution_hook` while you are trying things out. It is session-scoped, and
you can clear it.
</Aside>

### The veto reaches the caller

Asking the desk to raise a credit note now produces this:

```
[hook] run of SC_DESK by UC_AI starts.
The veto stopped the run: ORA-20990: The desk cannot raise a credit note
outside office hours.
```

Read that carefully, because it is the point of the lesson:

- The error came **out of `execute_agent`**. It is not a tool result the model gets
  to reason about, and not a sentence it can explain away. The run is over.
- `before_execution` had already run, so the hook can see a run start and stop it
  later.
- `after_execution` still fired, and recorded the failed run:

```
EXEC_ID  STATUS   INPUT_TOKENS  OUTPUT_TOKENS
   5073  failed              0              0
```

<Aside type="note" title="A failed run records no tokens and no messages">
Both are `0`, and `message_count` on the session is `0` too. UC AI has no result
object to read them from when a run raises. So `tool_calls_count = 0` on a failed
row does **not** mean no tool ran. This is the same point as
[lesson 4](/products/uc-ai/docs/tutorial/service-contract-desk/04-see-what-it-did/): count the
`tool_call` rows when you need the truth.
</Aside>

`before_tool_call` also fires for a plain `uc_ai.generate_text` call, not only for
an agent run. So a hook is a schema-wide control, not an agent-level one.

## Ship it

Your prompt profile, your tools and your agent are **rows**. They are not in your
repository, and a deployment of your packages does not carry them. So the
deployment is a script.

`09_promote.sql` is that script. It is written to be run more than one time, so the
same file is the install and the upgrade:

<Steps>

1. **Tools** with `merge_tool_from_schema`, which is create-or-replace for a tool.

2. **The profile**, created when absent and updated when present, at an explicit
   version.

3. **The agent**, created when absent and left alone when present.

4. **Memory, then the two activations.** `enable_for_agent` writes the memory tag
   into the profile version the agent resolves to **now**, so it must run after the
   profile exists — and again whenever you ship a new profile version.

</Steps>

What the script deliberately does **not** carry:

| Not deployed | Why |
| --- | --- |
| The demo tables | Your real tables are already there |
| The run history | The history of a development schema is not production data |
| The memory stores | What the desk learned in development is not true in production |

A release log should end with this:

```
OBJECT    DETAIL
tools     4
profile   SC_DESK_PROFILE v1 active
agent     SC_DESK v1 active
memory    context on contract_id
```

### Switching it off, and removing it

Two different needs, two different calls:

```sql
-- Stop it answering. Keeps every row, and is reversible.
uc_ai_agents_api.change_status('SC_DESK', 1, uc_ai_agents_api.c_status_archived);

-- Remove it and everything that belongs only to it.
uc_ai_agents_api.purge_agent(p_code => 'SC_DESK');
```

`change_status` to `archived` is the kill switch. An archived agent no longer
resolves, so a queued job fails with a clear error instead of doing something you
did not want.

`purge_agent` removes every version of the agent, its executions, its sessions,
their messages, and the memory stores that belong to it alone. It **keeps** what
other things also use: a shared or global memory store, a session another agent
opened, and the prompt profile — a profile lives without an agent, and another
agent can use it. It also keeps a tool whose PL/SQL text names the agent, because a
tool only mentions it in a string.

<Aside type="caution" title="Purging deletes an audit trail">
`purge_agent` removes run history. Decide whether you are allowed to do that before
you run it in production. If you only want the agent to stop, archive it.
</Aside>

## Verification

```sql
select 'sessions' as what, to_char(count(*)) as detail
  from uc_ai_agent_sessions
 where root_agent_id = ( select id from uc_ai_agents where code = 'SC_DESK' )
union all
select 'audit rows', to_char(count(*)) from sc_desk_audit
union all
select 'tokens today'
     , to_char(nvl(sum(total_input_tokens + total_output_tokens), 0))
  from uc_ai_agent_sessions
 where started_at >= trunc(sysdate);
```

Then clear the hook, so it does not affect your next experiment:

```sql
begin
  uc_ai_agents_api.set_execution_hook(null);
end;
/
```


## What you built

Nine lessons ago the model could not see your data. Now:

- It reads four tables through tools that **cannot** name a contract, so an
  engineer on contract 88 can never be shown contract 99.
- It can raise a credit note, and the **database** decides whether that is allowed,
  in four conditions written in PL/SQL rather than in English.
- It remembers each contract between conversations.
- It answers in fields your page can render, from a background job that does not
  block the page.
- Every run is recorded: who, when, which tools, how many tokens.

## Key takeaways

- Core records tokens, not money. Multiply by your own rate, or use Guardrails for
  real spend control.
- A hook raise in `before_tool_call` ends the run. It is not a refusal the model can
  explain, which is what makes it a control rather than a suggestion.
- `uc_ai_agents_api.purge_agent(p_code => 'SC_DESK');` removes the agent and its
  history. `change_status(..., c_status_archived)` is the reversible one.
