## Two different problems

The desk answers one question at a time and forgets everything. Those are two
problems with two different answers:

- An engineer asks "and is that one inside the coverage window?". The desk does not
  know what "that one" is. **A session** fixes this.
- Tomorrow another engineer opens the same contract. Everything the desk learned
  today is gone. **Memory** fixes this.

**Without a session,** every turn starts from nothing. **Without memory,** every
conversation starts from nothing.

## A session keeps one conversation together

Every run so far let UC AI generate its own session id, so every run was a
conversation of one turn. Pass a session id of your own, and the second call
continues the first. A follow-up sends `p_follow_up_message` instead of new input
parameters:

```sql
declare
  l_result  json_object_t;
  l_session varchar2(255 char) := uc_ai_agents_api.generate_session_id;
begin
  l_result := uc_ai_agents_api.execute_agent(
    p_agent_code       => 'SC_DESK'
  , p_input_parameters => json_object_t('{"engineer_name":"Petra","today":"2026-08-24"
      ,"question":"Which invoice on this contract still has an uncredited amount?"}')
  , p_session_id       => l_session
  , p_run_context      => json_object_t('{"contract_id":"88","engineer":"petra.k"}')
  );
  sys.dbms_output.put_line('TURN 1: ' || l_result.get_clob('final_message'));

  -- The follow-up names no invoice. The session carries the first answer.
  l_result := uc_ai_agents_api.execute_agent(
    p_agent_code        => 'SC_DESK'
  , p_follow_up_message => 'And is that one inside the coverage window?'
  , p_session_id        => l_session
  , p_run_context       => json_object_t('{"contract_id":"88","engineer":"petra.k"}')
  );
  sys.dbms_output.put_line('TURN 2: ' || l_result.get_clob('final_message'));
end;
/
```

<AiOutput model="gpt-5.6-terra" date="2026-08-24" label="Two turns, one session">
**Turn 1:** INV-1001 has $780 still uncredited and is within coverage.

**Turn 2:** Yes — INV-1001 is inside the coverage window.
</AiOutput>

Turn 2 never said `INV-1001`. The session did.

## Memory keeps knowledge between conversations

One call gives the desk a memory, and scopes it to the contract:

```sql
begin
  uc_ai_memory.enable_for_agent(
    p_agent_code  => 'SC_DESK'
  , p_scope       => uc_ai_memory.c_scope_context
  , p_context_key => 'contract_id'
  );
  commit;
end;
/
```

Memory is a virtual filesystem in Oracle tables, rooted at `/memories`. The desk
reaches it through one `MEMORY` tool that follows the contract of the Anthropic
memory tool, so it works on every provider, OpenAI included.

The `context` scope keys the store on a run-context value, so **each contract gets
its own memory**. Contract 88 and contract 99 cannot read each other's files. The
same `contract_id` that binds the tools in lesson 3 does a second job here.

`enable_for_agent` adds the memory tag to the model configuration and keeps the tag
lesson 3 put there:

```
{"g_max_tool_calls":8,"g_tool_tags":["scdesk","memory"],"g_enable_tools":true}
```

<Aside type="caution" title="From now on, every run needs the run context">
Once memory is scoped to `contract_id`, a run that does not supply it cannot be
matched to a store, and UC AI stops the run before it starts:

```
ORA-20426: The memory of agent "SC_DESK" is scoped to the run-context key
"contract_id", which this run does not supply. Pass it in p_run_context, for
example json_object_t('{"contract_id":"123"}').
```

The lesson 2 pattern, `execute_agent` with no `p_run_context`, stops working here.
Memory changes the contract of the agent that you call.
</Aside>

## Two separate conversations

Now the test. Two runs, each with a **new** session, so nothing carries over
except the memory. The first one tells the desk something that is in no table:

> **Conversation 1:** Remember for next time: this customer always wants the plant
> manager Anna Ruiz copied on any credit note, and they prefer email over phone.

<AiOutput model="gpt-5.6-terra" date="2026-08-24" label="Conversation 1" quiet>
Noted: copy plant manager Anna Ruiz on any credit note, and use email rather than
phone.
</AiOutput>

The second one is a new conversation that was told none of it, and it asks:

> **Conversation 2:** I am about to raise another credit note for this customer.
> Anything I should know about how they want to be contacted?

<AiOutput model="gpt-5.6-terra" date="2026-08-24" label="Conversation 2">
Use email rather than phone, and copy plant manager Anna Ruiz on every credit
note.
</AiOutput>

Nothing in conversation 2 named Anna Ruiz. No table holds her name either. The
desk read the file it wrote in conversation 1.

## Verification

The view lists the files and their size:

```sql
select store_key
     , path
     , char_count
  from uc_ai_v_memory_files
 where agent_code = 'SC_DESK'
 order by path;
```

```
STORE_KEY                        PATH                                             CHAR_COUNT
context:SC_DESK:contract_id:88   /memories/contract_invoice_status.txt                   176
context:SC_DESK:contract_id:88   /memories/customer_communication_preference.txt         152
```

The store key holds four parts: scope, agent, key, and value. An operator can read
or delete the memory of one contract from that string alone.

The view carries **no content column**, so read a file through the API:

```sql
declare
  l_store_id number;
begin
  l_store_id := uc_ai_memory.resolve_store_id(
    p_scope         => uc_ai_memory.c_scope_context
  , p_agent_code    => 'SC_DESK'
  , p_context_key   => 'contract_id'
  , p_context_value => '88'
  );

  sys.dbms_output.put_line(
    uc_ai_memory.get_file(l_store_id, '/memories/customer_communication_preference.txt'));
end;
/
```

```
Current contract customer preference (recorded 2026-08-24): Copy plant manager
Anna Ruiz on every credit note. Customer prefers email rather than phone.
```

The desk chose the filename and the wording. Nothing in your code told it to write
a file, or what to call it. A `MEMORY PROTOCOL` block that UC AI adds to the
rendered system prompt did.

### Tell it what to record

That block is the same text for every agent, and it says only "record important
context". What counts as important at your desk is your decision, and the place to
write it down is the system prompt of the prompt profile:

```text
MEMORY
Record what a conversation told you and no table holds: how this customer wants
to be contacted, who must be copied, what was agreed on the phone.
Do not record anything a tool can read: invoice totals, credited amounts and
coverage dates come from the tools, every time.
Keep one file for each subject, and rewrite a line that stops being true.
```

Update the profile the way lesson 3 updated the model configuration: read the row
with `get_prompt_profile`, set `system_prompt_template`, and pass the row back.
[Give an Agent a
Memory](/products/uc-ai/docs/tutorial/give-an-agent-a-memory/03-decide-what-it-writes/)
is a whole lesson on this, with the file layout and a note that goes out of date.

## When a memory change takes effect

A memory change reaches the **next new session**. An open conversation keeps the
system prompt it started with, so it also keeps the memory rules it started with.

`enable_for_agent` writes the memory tag into the profile version the agent
resolves to now. `uc_ai_prompt_profiles_api.create_new_version` copies
`model_config_json`, so a version made that way carries the tag with it. A version
you build from scratch carries whatever configuration you pass it.

<Aside type="note" title="A store is created at its first use">
`resolve_store_id` reports `ORA-20423` for a contract whose agent has never run,
because the store does not exist yet. A script that clears the memory before it
starts must allow for that:

```sql
declare
  e_no_store exception;
  pragma exception_init(e_no_store, -20423);
begin
  -- resolve and clear
exception
  when e_no_store then
    null;  -- no store yet, so it is already empty
end;
```
</Aside>

## Key takeaways

- A session solves "and is that one inside the window?". Memory solves "what did we
  agree last week?". They are different problems.
- The `context` scope gives one memory per business object, keyed on the same
  run-context value that binds your tools. Read [what `user` scope
  separates](/products/uc-ai/docs/guides/agent-memory/#what-user-scope-separates)
  before you reach for `user`: it keys on the signed-in user, not on your records.
- `uc_ai_memory.enable_for_agent(p_agent_code => 'SC_DESK', p_scope => 'context', p_context_key => 'contract_id');`

**Full reference:** [Agent memory](/products/uc-ai/docs/guides/agent-memory/)
covers every scope, the size caps, and housekeeping.
