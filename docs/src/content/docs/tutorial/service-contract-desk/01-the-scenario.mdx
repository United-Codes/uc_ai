## What you build in this course

You build the **service-contract desk**: an agent that answers questions about one
service contract and can raise a credit note against an invoice on it.

A support engineer opens a contract and asks the agent about it. The agent reads
the contract, its service calls, and its invoices. When the engineer asks for a
credit note, the **database** decides whether the contract allows it.

Two words from this domain, because the lessons use them:

- A **credit note** cancels part of an invoice. It is money the customer does not
  pay.
- A contract has a **coverage level**. `GOLD` covers parts and labour. `SILVER`
  covers labour only.

## Before you start

<Aside type="caution" title="One step needs a DBA">
A database cannot call an HTTPS API until somebody grants it a network ACL. Many
systems also need the provider certificate in a wallet. Plan about 20 minutes,
and ask your DBA early. The [network setup
guide](/products/uc-ai/docs/guides/network-setup/) has the grants.
</Aside>

Three more facts, before you run anything:

- **Contract data leaves the database.** Every lesson sends part of your prompt to
  OpenAI over HTTPS. If your data cannot leave the database, use
  [Ollama](/products/uc-ai/docs/providers/ollama/) or
  [OCI](/products/uc-ai/docs/providers/oci/) instead. Change the provider constant
  and the model constant. The rest of the course is the same.
- **The course is cheap.** Every lesson together is well below one dollar at
  current prices. One recorded lesson used 574 input tokens and 27 output tokens.
- **The recorded output comes from `gpt-5.6-terra`.** A smaller model works, but it
  needs better tool descriptions when you register the tools.

## Your first answer

`uc_ai.generate_text` is the smallest thing UC AI does. Give it a prompt, a
provider, and a model. It returns the answer of the model.

The model knows nothing about your database. So the first idea most people try is
to put the rows into the prompt:

```sql
declare
  l_rows   clob;
  l_result json_object_t;
begin
  select json_arrayagg(
           json_object('invoice_no' value i.invoice_no
                     , 'total'      value i.parts_amount + i.labour_amount)
           returning clob)
    into l_rows
    from sc_invoices i
   where i.contract_id = 88;

  l_result := uc_ai.generate_text(
    p_user_prompt   => 'How many invoices are on this contract?' || chr(10)
                       || 'Contract data:' || chr(10) || l_rows
  , p_system_prompt => 'You are the service-contract desk. Answer from the contract data only.'
  , p_provider      => uc_ai.c_provider_openai
  , p_model         => uc_ai_openai.c_model_gpt_5_6_terra
  );

  sys.dbms_output.put_line(l_result.get_clob('final_message'));
end;
/
```

This works:

<AiOutput model="gpt-5.6-terra" date="2026-08-24">
There are 3 invoices on this contract.
</AiOutput>

## Where this approach stops

Now ask a question the pasted rows do not answer. The rows hold an invoice number
and a total. They do not hold how much of each invoice is already credited:

> **Q:** How much can I still credit on INV-1003?

<AiOutput model="gpt-5.6-terra" date="2026-08-24" wrong>
You can still credit up to 200 on INV-1003.
</AiOutput>

That answer is wrong. The correct answer is **0**. Invoice INV-1003 is already
credited in full, and the database knows it. The next `select` on this page proves
it.

The model did nothing strange. It saw a total of 200, it saw no credit
information, and it assumed the total was available. The reasoning is good. The
data was incomplete, and nothing in the prompt said so.

This is the failure that matters, because it is quiet:

- **You** had to know which rows matter, before the engineer asked the question.
- You pasted invoice numbers and totals, so the model is blind to credits,
  coverage windows, service calls, and assets.
- A wrong number here becomes a **second credit note** on an invoice that is
  already paid back in full.

You cannot correct this by pasting more rows. A real contract joins six tables,
and no prompt holds all of them. The model must be able to **ask your database**
instead.

That is what the rest of the course builds.

<Aside type="note" title="The model can also refuse">
Sometimes the same question gets "the remaining creditable amount cannot be
determined" instead. Both answers prove the same point: the model cannot know.
Never build on an answer the model had no data for.
</Aside>

## Verification

Run this to see the four invoices, and what the credit-note rule must decide for
each one. Lesson 5 makes the database enforce this column:

```sql
select i.invoice_no
     , c.coverage_level
     , i.parts_amount + i.labour_amount as invoice_total
     , nvl(( select sum(cn.amount)
               from sc_credit_notes cn
              where cn.invoice_id = i.id ), 0) as credited
  from sc_invoices i
  join sc_contracts c on c.id = i.contract_id
 order by i.invoice_no;
```

Your output must match this, because the setup script fixes every value:

```
INVOICE_NO   COVERAGE_LEVEL   INVOICE_TOTAL   CREDITED
INV-1001     GOLD                       780          0
INV-1002     GOLD                       350          0
INV-1003     GOLD                       200        200
INV-2001     SILVER                     850          0
```

`INV-1003` has 200 of 200 credited. So the answer the model gave above was wrong
by the full amount.


## Key takeaways

- A model that reads your data from the prompt can answer only the question you
  prepared for. Every other question needs data you did not paste.
- Incomplete data is more dangerous than missing data. The model reasons from what
  it has, and a plausible wrong number reads exactly like a right one.
- `uc_ai.generate_text` needs four things: `p_user_prompt`, `p_system_prompt`,
  `p_provider`, `p_model`.

**Full reference:** [generate_text](/products/uc-ai/docs/api/generate_text/) has
every parameter and the whole result structure.
